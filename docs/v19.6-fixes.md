# v19.6 — fast request actions and workflow concurrency fixes

## Request actions return immediately

Status changes, support movements, request creation, comments, acknowledgements, returns and closures no longer wait for SMTP delivery before returning control to the browser. Email delivery is dispatched after the request operation succeeds.

For local UAT, use `MAIL_MODE=console`. SMTP mode now uses configurable connection, greeting and socket timeouts and defaults to IPv4 to avoid long IPv6 connection stalls.

## Stale page and duplicate submission protection

- Status forms submit the status visible when the page was opened.
- Support movement forms submit the support level visible when the page was opened.
- The request service returns HTTP 409 when the request changed before submission.
- Re-submitting the already-current status is treated as a safe no-op.
- POST forms disable their submit button after the first valid submission.
- Request action errors return to the request page with a clear message and refresh link.

## Validation alignment

Status and support-movement comments now enforce the same minimum length in the browser and request service. Required movement comments must contain at least three characters.

## Operational note

The v19.6 background mail dispatch is process-local and non-durable. A later production hardening step should move notification delivery to a durable outbox/worker so messages survive a process restart.
